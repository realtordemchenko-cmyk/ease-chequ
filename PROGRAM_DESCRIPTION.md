# Program Description

## Управление заявками и агентами

### Жизненный цикл заявок
- **Requests** создаются при регистрации или импорте.
- Статусы: **Pending → Approved → Rejected**.
- Approved/Rejected заявки не удаляются, а переходят в архив (Resolved).
- Requests служат **аудиторским следом**, а не местом долгого хранения.

### Агенты (Agents)
- Создаются всегда, даже если **Board # отсутствует**.
- Если Board # не указан → агент получает статус **Draft**.
- **Draft‑агенты**:
  - отображаются в списке Agents с бэйджем Draft,
  - не имеют доступа и не могут генерировать inviteLink,
  - могут быть отредактированы администратором (добавление Board #).
- После добавления Board # агент переводится в **Inactive** или **Active**.
- Если Board # неверный, администратор корректирует его в карточке агента.
- **Дедупликация**:
  - первичный ключ — Board #,
  - вторичный — email,
  - при совпадении обновляется существующий агент, дубликат не создаётся.

### Клиенты (Clients)
- Создаются только при наличии минимально обязательных данных (имя).
- Могут быть привязаны к агенту или существовать отдельно.

### Логи (Logs)
- Все действия фиксируются.
- Новые записи добавляются **в начало** списка.
- Поддерживаются пагинация и экспорт (CSV/JSON).
- Логи не удаляются, обеспечивая полный аудит.

---

## Валидация и UX
- На лендинге/регистрации агент не может продолжить без полного комплекта данных.
- В админке администратор видит заявки с флагом *Requires info* и может либо запросить исправление, либо отклонить.
- В интерфейсе есть фильтры: *Active requests*, *Resolved requests*, *Requires info*.

---

## Расширяемость
- В будущем можно добавлять новые подтипы агентов (например, агентство) через схему/конструктор, без изменения кода.
- Валидация и обязательные поля описываются в схеме.
- Импорт групп агентов создаёт Draft‑агентов партиями, которые администратор доводит до Active.
